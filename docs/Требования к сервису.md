# Требования к сервису учёта подписок

Редакция 2 от 27 ноября 2026 года

## 1 Назначение

Сервис помогает пользователю вести список своих подписок на контент, сохранять сведения о фактических платежах и получать расходы за выбранный период. Деньги списывают провайдеры контента. Наш сервис не подключается к банкам, не выполняет списания и не хранит номера карт или счетов.

У всех пользователей одинаковые возможности. Каждый пользователь работает только со своими данными. Все суммы учитываются в рублях; выбор валюты не предусмотрен. Категории подписок, тарифные планы, роли администратора, прогнозы, календарь, восстановление пароля и автоматический перенос дат в учебную версию не входят. Требования к системному окружению не рассматриваются.

## 2 Функциональные требования

Идентификаторы ФТ сохранены из предыдущей редакции для сопоставления изменений; их актуальное содержание задано ниже.

ФТ-01 Регистрация. Пользователь регистрируется по email и паролю. Email проверяется, обрезается по краям и сравнивается без учёта регистра. Повторная регистрация одного адреса отклоняется. Пароль содержит от 12 до 128 символов.

ФТ-02 Вход. При правильных данных пользователь получает токен на 30 минут. Защищённые операции требуют действующий токен. Неверные данные входа, истёкший и отозванный токены не дают доступа. Дополнительная блокировка по числу неудачных входов не требуется.

ФТ-03 Выход. Пользователь отзывает текущую сессию. После выхода её токен перестаёт работать; другие сессии пользователя сохраняются. Восстановление пароля не реализуется.

ФТ-04 Подписки. Пользователь создаёт, просматривает и изменяет собственные подписки. DELETE переводит подписку в архив. Повторная архивация допустима. PUT может восстановить её из архива. История платежей при архивации сохраняется.

ФТ-05 Данные и валидация. У подписки есть название, стоимость одного периода, периодичность monthly или yearly, дата следующего платежа и статус active, paused или archived. Название содержит 1–100 символов после обрезания. Суммы положительны, не превышают 999999999.99 рубля и имеют не более двух дробных знаков. Некорректные и лишние поля запроса отклоняются с описанием ошибки.

ФТ-06 Список подписок. Список содержит только подписки владельца, поддерживает фильтр по статусу и страницы. Без фильтра возвращаются все статусы. Страница начинается с 1; размер по умолчанию 20, допустим от 1 до 100. Сортировка: дата следующего платежа по возрастанию, затем идентификатор. Пустая страница возвращается успешно.

ФТ-07 Фактические платежи. Пользователь вручную записывает сумму и дату уже совершённого платежа по своей подписке, в том числе архивной. Дата не позже текущего дня UTC. Сумма платежа может отличаться от стоимости подписки. Запись не запускает списание, не меняет статус и следующую дату подписки.

ФТ-08 История платежей. Пользователь получает свои платежи за период, при необходимости по одной подписке. Поддерживаются страницы. Период [from, to) включает from и исключает to; обе даты обязательны, from < to. Сортировка: дата платежа по убыванию, затем идентификатор по возрастанию. Чужая и отсутствующая подписка не раскрываются.

ФТ-09 Расходы. За тот же период сервис возвращает общую сумму фактических платежей и суммы по подпискам. Платежи архивных подписок учитываются. Название берётся из текущей записи подписки. При отсутствии платежей итог равен 0.00, список по подпискам пуст. Расчёт по периодичности без внесённых платежей не выполняется.

ФТ-10 Прогноз расходов исключён из объёма. Периодичность и следующая дата хранятся только как сведения о подписке.

ФТ-11 Календарь и автоматические списания исключены. Платежи не создаются автоматически; даты пользователь меняет вручную.

ФТ-12 Защита от повторов. При записи платежа клиент передаёт Idempotency-Key. В течение 24 часов повтор того же пользователя с теми же подпиской, суммой и датой возвращает первоначальный платёж, а другие данные с тем же ключом дают конфликт. Ровно через 24 часа ключ можно использовать заново. Одновременные повторы не должны создавать несколько платежей.

## 3 Нефункциональные требования

НФ-01 Структура. Приложение является монолитом с тремя слоями: HTTP API, бизнес-логика, доступ к данным. В контроллерах нет бизнес-расчётов и запросов к БД. Бизнес-логика не зависит от ORM и HTTP. Доступ к данным выполняется через ORM и миграции.

НФ-02 Поддерживаемость. Каждый класс, DTO и интерфейс находится в отдельном файле. Имена отражают назначение, методы имеют понятную ответственность. Program.cs содержит запуск и настройку зависимостей. README объясняет запуск и проверку. Дополнительные сервисы и абстракции без задачи не вводятся.

НФ-03 Контроль доступа. Пользователь определяется по токену, а не по полю userId в запросе. Список, чтение, изменение, архивация, запись платежей и расчёт расходов ограничены владельцем. Для отсутствующей и чужой подписки возвращается одинаковый 404. Роли и разные права пользователей не вводятся.

НФ-04 Защита паролей. Пароли хранятся как стойкий хеш с солью, создаваемый специализированным PasswordHasher. Открытый пароль, токен и их содержимое не записываются в журнал. В БД хранится хеш токена. Клиентские обращения выполняются по HTTPS. Обратимое шифрование паролей не применяется.

## 4 Требования качества и надёжности

КЧ-01 Проверяемость. Все бизнес-сервисы покрываются изолированными юнит-тестами. Доступ к данным, часы и криптографические адаптеры подменяются. Проверяются положительные сценарии, ошибки и границы. Цель лабораторной — не менее 80% ветвей и 90% операторов бизнес-логики. Метрики строк и операторов указываются раздельно; если операторы не измерены, критерий отмечается как неподтверждённый.

КЧ-02 Понятные ответы. API имеет согласованный контракт с примерами, ограничениями и статусами. Ошибки содержат code, message, requestId; ошибки валидации также содержат errors. Внутренние стеки клиенту не возвращаются.

НД-01 Сохранность данных. Пользователи, сессии, подписки, платежи и ключи повторов сохраняются в БД и доступны после перезапуска. Архивация не удаляет историю. Начальная схема создаётся миграцией.

НД-02 Атомарность. Платёж и ключ сохраняются одной транзакцией: оба изменения применяются либо оба отменяются. Внешние ключи и уникальные индексы защищают целостность. Параллельные запросы с одним ключом создают один платёж.

НД-03 Ошибки БД. Проверка готовности проверяет соединение и наличие схемы. При недоступной БД возвращается 503 без технических подробностей. Восстановление из резервной копии, показатели доступности и нагрузочные нормативы в учебную задачу не входят.

## 5 Критерии приёмки

Решение собирается, запускается и предоставляет согласованные маршруты. Выполняются проверки регистрации, входа, CRUD подписки, фильтра, истории, расходов, повторов платежа и доступа второго пользователя. Проходят юнит-тесты и интеграционные тесты с временной реальной БД. Результаты сборки, тестов и покрытия указываются по факту; прошлые результаты не считаются подтверждением изменённой реализации.
