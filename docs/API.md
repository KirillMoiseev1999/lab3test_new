# Контракт API сервиса учёта подписок

Редакция 2. Контракт задаёт целевую упрощённую реализацию. До изменения кода работающий сервер может ещё отвечать по предыдущей редакции из archive/before-simplification.

Базовый путь `/api/v1`, HTTPS, JSON UTF-8. Все суммы в рублях; поле currency отсутствует. Машиночитаемая спецификация: [openapi.json](openapi.json). Категорий, тарифов и ролей нет.

## Маршруты

| Метод | Путь | Успех | Особые ошибки |
|---|---|---|---|
| POST | /auth/register | 201 | 400, 409 |
| POST | /auth/login | 200 | 400, 401 |
| POST | /auth/logout | 204 | 401 |
| POST | /subscriptions | 201 | 400, 401 |
| GET | /subscriptions | 200 | 400, 401 |
| GET | /subscriptions/{id} | 200 | 400, 401, 404 |
| PUT | /subscriptions/{id} | 200 | 400, 401, 404 |
| DELETE | /subscriptions/{id} | 204 | 400, 401, 404 |
| POST | /subscriptions/{id}/payments | 201 | 400, 401, 404, 409 |
| GET | /payments | 200 | 400, 401, 404 |
| GET | /analytics/expenses | 200 | 400, 401 |
| GET | /health/ready | 200 | 503 |

Все пути относительно /api/v1. Внутренняя ошибка даёт 500; недоступность БД — 503. Register, login и health доступны без токена; остальные требуют `Authorization: Bearer <accessToken>`. Отсутствующий и чужой объект дают одинаковый 404. Некорректный GUID и лишние поля JSON дают 400. userId клиент не задаёт.

## Регистрация и сессия

Тело register и login:

```json
{"email":"student@example.com","password":"Lab3-demo-pass-2026"}
```

Email до 254 символов после обрезания, уникален без учёта регистра; пароль 12–128 символов без обрезания. Register возвращает id,email. Login возвращает accessToken,tokenType=Bearer,expiresAt в UTC. Срок 30 минут, в момент expiresAt токен уже недействителен. Logout возвращает 204 без тела и отзывает только текущую сессию. Лимита неудачных попыток в учебном контракте нет.

## Подписки

Тело POST и PUT, все пять полей обязательны:

```json
{"name":"Яндекс Плюс","price":"399.00","frequency":"monthly","nextPaymentDate":"2026-12-01","status":"active"}
```

Название 1–100 символов после обрезания. Price — строка от 0.01 до 999999999.99, до девяти цифр до точки и двух после, без пробелов, знака и экспоненты. Выходной формат всегда с двумя знаками. Frequency: monthly/yearly; status: active/paused/archived. NextPaymentDate — существующая дата yyyy-MM-dd, справочное поле без автоматического переноса. Ответ содержит id и пять полей. PUT заменяет редактируемые поля, может восстановить архивную подписку; DELETE архивирует, повтор также 204.

GET списка допускает status,page,pageSize. Без status включены все статусы. Page от 1, pageSize 1–100, по умолчанию 1 и 20. Сортировка nextPaymentDate, затем id по возрастанию. Ответ:

```json
{"items":[],"page":1,"pageSize":20,"totalCount":0}
```

## Платежи и идемпотентность

POST платежа требует один заголовок `Idempotency-Key`, 1–128 символов после обрезания. Тело:

```json
{"amount":"100.00","paidOn":"2026-11-27"}
```

Ограничения суммы совпадают с price; paidOn — существующая дата не позже текущего дня UTC. Сумма может отличаться от цены подписки. Архив допускает запись платежа. Никакого списания и изменения подписки эта операция не выполняет. Ответ:

```json
{"id":"11111111-1111-1111-1111-111111111111","subscriptionId":"22222222-2222-2222-2222-222222222222","amount":"100.00","paidOn":"2026-11-27"}
```

Ключ действует в пределах пользователя. Менее чем через 24 часа совпадение subscriptionId, числовой суммы и paidOn возвращает тот же платёж и 201; другие реквизиты дают 409. Суммы 100 и 100.00 эквивалентны. Ровно через 24 часа возможен новый платёж с тем же ключом. Старый платёж сохраняется. Параллельные повторы атомарны.

GET /payments требует from,to, допускает subscriptionId,page,pageSize. Полуинтервал [from,to), обе даты обязательны, from < to. Размеры страниц такие же, как у подписок. Ответ имеет items,page,pageSize,totalCount. Сортировка paidOn по убыванию, затем id по возрастанию. Архивные платежи включены; фильтр чужой или отсутствующей подписки даёт 404.

## Расходы

GET /analytics/expenses требует from,to с теми же правилами. Суммируются только внесённые платежи владельца за период, включая архивные подписки. По периодичности подписки расходы не рассчитываются. Ответ:

```json
{"total":"300.00","bySubscription":[{"subscriptionId":"22222222-2222-2222-2222-222222222222","name":"Яндекс Плюс","amount":"300.00"}]}
```

Список содержит подписки с платежами в периоде, название текущее, порядок по subscriptionId по возрастанию. Если платежей нет: total=0.00 и bySubscription=[]. Все значения в рублях, категорий и группировки по валютам нет.

## Готовность и ошибки

GET /health/ready возвращает 200 и {"status":"ready"} при доступной БД с актуальной схемой; иначе 503 с общей ошибкой.

```json
{"code":"validation_error","message":"Некорректные данные.","requestId":"...","errors":{"price":["Сумма должна быть положительной."]}}
```

Ошибки: validation_error — 400; invalid_session — 401; subscription_not_found — 404; email_already_registered и idempotency_conflict — 409; internal_error — 500; database_unavailable — 503. Errors используется для валидации. При 401 передаётся WWW-Authenticate: Bearer. Стеки и детали БД клиенту не выдаются.
